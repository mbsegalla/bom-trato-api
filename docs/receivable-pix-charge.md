# Phase 4.3 — static Pix payment instructions

`GET /api/organizations/:organizationId/receivables/:receivableId/pix-charge` prepares a BR Code for the current outstanding BRL amount. The verified organization owner must have platform access; the same ownership policy as receiving settings applies because a static payload contains the receiving key. A repeatable-read transaction reads both the tenant-scoped receivable and destination configuration. There are no writes, no calls to a bank or PSP and no payment record is created.

The endpoint returns organization/receivable IDs, receivable and receiving-settings versions, amount in cents, currency, configured merchant display label, a stable 25-character alphanumeric reference (lossless base-36 encoding of the receivable UUID) and the Pix copy-and-paste string. It uses the static fields and CRC16 (polynomial 0x1021, initial value 0xFFFF) described in the Banco Central Manual de Padrões para Iniciação do Pix, sections 2.5–2.6: https://www.bcb.gov.br/content/estabilidadefinanceira/pix/Regulamento_Pix/II_ManualdePadroesparaIniciacaodoPix.pdf . The checksum checks encoding integrity, not the bank account or authenticity. The payer must confirm the actual bank-returned recipient and amount in their banking app.

Only OPEN/PARTIALLY_PAID receivables with a positive, consistent remaining balance can generate instructions. Paid/canceled receivables and missing/disabled destinations are rejected. The payload is generated from the balance at the read snapshot, not a payment authorization or a guarantee of the latest amount after the response. A static code can be reused and cannot be revoked by Bom Trato after sharing. Regenerate after a balance or destination change; reconcile manually against a bank receipt before recording payment. The reference is not a unique bank transaction ID or proof of payment; multiple transfers may carry it.

No new migration, API environment variable or backend package. Phase 4.2 migration and the same receiving encryption secret are required. Never log the response payload or pass it to third-party QR generators. Before release run policy tests, validate private cache headers and owner/tenant isolation, test partial payments, disabled/malformed destinations and scan generated test codes in a banking sandbox or app without submitting payment. Provider-backed dynamic charges, revocable payment links, confirmation webhooks and reconciliation are later increments.
